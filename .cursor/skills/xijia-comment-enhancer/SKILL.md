# AI 注释增强与维护

## 目标

为**核心业务代码**按统一维度补全或更新**语义注释**：区分端点层与内部层，`[业务逻辑]` 写业务含义。本技能约定格式与方法论；栈无关。

生成或更新注释前**必须** Read [`references/comment-format.md`](references/comment-format.md)。

## 何时启用

- 新增或修改**核心业务代码**（对外入口、业务处理单元、工具 / Helper、复杂私有方法）
- 用户要求补注释 / 增强注释
- 逻辑变更后需追加 `[修改记录]`
- 提交前检查目标方法注释

自解释一行函数、纯数据结构、getter/setter 等非核心不强制。

## 执行步骤

1. **判定方法类型**：端点 / 内部（维度表见 comment-format）。  
   **完成：** 类型已判定且维度集不混用。
2. **取证**：入口标识、方法体业务步骤、数据资源/外部依赖；有前端时先文件后菜单（见 comment-format）。  
   **完成：** 必填维均有证据或已判定可省略可选维。
3. **生成/更新注释**：必填维齐全；`[业务逻辑]` 与源码逐步对应。  
   **完成：** 注释块符合 comment-format。
4. **修改记录（仅逻辑变更）**：追加 `[YYYY-MM-DD] [需求名] - [简述]`，不删历史。  
   **完成：** 有变更则已追加，无变更则跳过。
5. **自检**：与源码一致；无泛化模板句/空壳调用句；可选维有证据才出现。  
   **完成：** comment-format「完成检查」清单全勾，或等价自检通过。

## 强制约束

- 严禁臆测；可选维无证据则省略。
- 语义优先于结构：维度齐全 ≠ 合格。
- 批量自下而上；只改注释不改逻辑。

## GOTCHAS

| 症状 | 根因 | 修复 |
| --- | --- | --- |
| 端点/内部维度混用 | 分层错误 | 端点用 `[功能描述]`，内部用 `[核心目的]` |
| `[业务逻辑]` 空壳调用句 | 未总结底层 | 先补内部层再写端点摘要 |
| verify 才补注释 | 违反 E.0 | 写代码阶段同步，guard 兜底 |
| `[涉及数据表]: 无` | 禁止占位 | 无证据则省略 |
| 臆测菜单/表名 | 无证据 | codegraph 或省略 |
