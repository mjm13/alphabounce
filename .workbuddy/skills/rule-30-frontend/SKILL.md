# 定位说明

本文件是 **前端技术规则的唯一入口**。契约一致性、目录组织、状态策略、异步交互（含按钮 loading）等前端实现约束均在此维护；**不再拆分独立前端规则文件**。

与后端分工：后端 domain / API 承载业务真值；前端负责展示、交互与契约对齐，不复制业务规则真相源。具体框架、组件库、测试命令由 `AGENTS.md` 与已安装栈技能约定。

# 主旨

前端实现以「契约一致性 + 能力边界清晰 + 可维护交互」为核心，避免页面层承载业务规则真相。

# 架构与组织

实际结构以 `frontend/src/` 下的目录为准（读代码即得），本规则不镜像目录树。

约定：

| 原则 | 说明 |
| --- | --- |
| 视图薄 | `views/` 负责数据加载与布局；业务 UI 与交互逻辑放 `components/` 的对应 Panel |
| 请求集中 | 后端调用统一走 `api/`，组件内不直接拼 URL |
| 复用下沉 | 跨 Panel 复用的逻辑下沉 `composables/`，样式下沉 `assets/styles/`（分层见 `docs/patterns/README.md`） |
| 与后端对齐 | 组件与 Tab 划分尽量与限界上下文 / 菜单模块一致，命名与 `docs/domain`、契约字段一致 |

# 契约与业务边界（硬约束）

- 前后端交互必须遵循已确认契约（路径、参数、返回语义、错误码）。
- 模块命名与能力边界保持一致；跨模块协作走显式契约，不靠隐式共享状态。
- **不在前端固化后端业务真值**；校验、权限、状态机以后端与契约层为准。
- 出现契约冲突时，**先升级规格/契约，再调整实现**；禁止在前端「兜底修语义」。
- 类型定义与 API 响应结构须与契约一致；字段含义不明时 stop-and-report，不臆测。

# 状态与数据（方向）

| 类型 | 说明 |
| --- | --- |
| 服务端状态 | 接口数据走专用数据客户端：缓存、失效、重试 |
| 全局 UI 状态 | 按域切分，避免单一巨型 store |
| 组件局部状态 | 能局部 state 解决的不提升到全局 |
| 业务规则 | 不在前端 duplicate；仅做展示所需的派生/格式化 |

# 异步交互：按钮 loading 与防重复提交

凡触发后台 API、文件下载、长耗时异步操作的按钮，必须在请求进行中展示 loading 并禁止重复提交。

## 硬约束（Must）

1. **独立 loading 状态**：每个异步操作按钮使用独立 loading 标识；多按钮共用同一 loading 时须确认不会互相误禁用。
2. **组件绑定**：按钮须同时绑定 loading 与 disabled（loading 期间不可再次触发）。
3. **入口防抖**：异步处理开头检查 loading，在 `try/finally`（或等价机制）中复位，避免竞态双点。
4. **覆盖范围**：提交/保存、删除确认、导出、批量任务、独立发请求的查询、上传、任何等待后台接口的点击操作。
5. **新建/改造默认遵守**：新增页面或改造现有按钮时，未加 loading 视为未完成。

## 豁免（可不单独 loading）

- 纯前端路由跳转且无 API。
- 仅打开/关闭本地弹窗、折叠面板。
- 列表/表格级 loading 已覆盖且按钮在请求期间不可见或已一并禁用（须在实现记录中说明）。

# 升级触发（When to Escalate）

- 接口语义不一致、字段含义不明确、权限边界冲突 → 升级到规格层决策。
- 无法用现有契约覆盖交互场景 → 先补契约再编码。
- 出现 Panel 之间循环依赖 → 先把共享逻辑下沉 `composables/`，不 shortcut 互引。

# 验收口径（Done Means）

- 交互行为、接口契约、能力命名三者一致。
- 变更可通过回归验证（见 `xijia-frontend-test` 技能），且不引入跨模块语义漂移。
- 触发后台请求的按钮：独立 loading + disabled + 处理入口防抖（见「异步交互」）。
- 服务端状态与 UI 状态职责清晰，无前端硬编码业务真值。
