# 触发条件（命中任一即必须执行）

- 本次 change **新增或修改**核心业务代码：API 端点、业务处理单元、跨模块编排、复杂私有方法
- 本次 change 新增或修改核心业务模型 / 持久化模型（如承载菜单、角色、权限、组织等业务语义的实体）
- 修改核心业务规则、关键流程分支
- 用户要求补全/增强注释

# 可跳过白名单（仅以下情形允许跳过，须逐条对应到 diff）

- 本次 **仅** 改文档、配置、样式、依赖版本，未触达核心业务代码
- 本次 **仅** 改测试文件，且未改被测业务实现
- guard 报告的非业务壳层文件（应用入口、路由配置、全局样式、构建配置等）——须在输出中点名并说明其非业务性质

> 白名单之外确实无法当次补齐时：写入 `docs/requirements/backlog.md` 并标注为阻塞项，然后停下报告——进度压力不改变 guard 结论。

# 写代码阶段门禁（不得推迟到 verify）

1. **新增核心业务代码时**：同一次编辑必须按 `xijia-comment-enhancer` 格式输出语义注释；不得先写裸代码、收尾再补。
2. **修改核心业务代码时**：必须同步检查并更新该方法/类/端点的既有语义注释；注释缺失时同改动一起补齐。
3. 若 afterFileEdit guard 提醒文件无语义注释标签，下一步优先补该文件注释，除非该文件属于白名单并向用户说明。

# 执行要求

1. **必须**调用 `xijia-comment-enhancer` 技能，按该技能规范执行（证据驱动、自下而上、只改注释不改逻辑）。
2. 顺序：先内部层（业务处理 / 辅助单元）→ 再端点层（对外 API 入口）。
3. 注释与代码语义保持一致，避免模板化空话；端点层与内部层维度不得混用。
4. 逻辑有变更时，端点/内部层注释须追加 `[修改记录]`。
5. **端点层**：每个对外入口前必须有独立注释块，且含 `[接口地址]` `[功能描述]` `[业务逻辑]`。
6. **存在前端目录且端点已在前端 API 层映射时**（路径见 `AGENTS.md`）：须按「先文件后菜单」取证补 `[前端路径]`；系统管理类 API 还须补 `[业务菜单]`。无前端调用证据的端点（如 health、restore-defaults、未封装 API）可省略。
7. **纳入范围与文件 glob**：端点层 / 内部层的具体路径约定见 `xijia-comment-enhancer/references/comment-format.md`（SSOT，`--check-comment-sync` 按其中的表校验）；本规则不写栈或语言专属文件名。

# verify 兜底门禁（客观校验，不接受纯自陈）

- 收尾时**必须**运行：`python .cursor/hooks/pipeline_guard.py --check-comment-sync`，并在验证输出中附其结论。
- guard exit≠0（存在无语义注释的变更实现文件，或端点注释块缺必填/UI 映射维）→ **不得**进入 Gate-2 或宣告完成；要么补注释、要么按白名单逐条说明并经用户确认。
- guard 会校验：① 文件级语义标签；② 每个端点块必填三维；③ 前端 API 层已映射端点的 `[前端路径]`/`[业务菜单]`（路径见 AGENTS.md）。
- 验证输出格式：
  - `Comment Sync: done — <文件清单> — guard: pass`
  - 或 `Comment Sync: skipped — <白名单条目> — guard: pass(无实现变更)`
