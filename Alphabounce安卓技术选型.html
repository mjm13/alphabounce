Alphabounce 安卓端技术选型

依据《Alphabounce 源码参考》—— 原版(Haxe→Flash) 与 Eternal-Twin 重写(Haxe→JS + PixiJS) 对照，目标是让游戏在 Android 上运行

① 现状与硬约束（来自源码参考）

版本技术形态安卓可行性
原版 Motion Twin Haxe 编译为 AVM1 / Flash SWF；只有客户端，无服务端；依赖外部 mt 库与 swfmake 不可行。 Flash 已停更，Android 不内置 Flash Player，Ruffle 也仅在浏览器内可行且非安卓原生。原版路线直接淘汰。
重写 Eternal-Twin Haxe→JS 前端 + PixiJS(WebGL) 渲染；Node + Redis 后端；Docker 部署；浏览器直跑 可行，且是现成入口。 本质已是一个 Web 游戏，安卓化的核心是"用 WebView 把它装进安卓壳"。

核心判断：源码已有 Web 形态（PixiJS/WebGL），所以安卓化的关键不是重写游戏逻辑，而是选择一种把 Web 游戏运行在 Android 上的封装方式，并把"后端依赖"降到最低。

② 三条安卓化路线

A
WebView 封装（推荐）—— 把前端静态站点塞进安卓 WebView，用 Capacitor 或原生 WebView 产出 APK/AAB。源码复用度最高、工作量最小。
B
原生重写—— 用 Kotlin + OpenGL/游戏引擎从零移植玩法。性能可控但等于重做，违背"复用源码"的目标，不推荐。
C
PWA 免打包—— Chrome "添加到主屏幕"，零构建。最简单但拿不到真正 APK、上架受限，适合快速验证。

④ 推荐方案：WebView 封装 + 后端本地化

  • 渲染层：保留 PixiJS（WebGL）。Android WebView 自 Android 5.0(API 21) 起支持 WebGL（需开启硬件加速）；低端机可让 PixiJS 回退到 Canvas 渲染。
  • 封装层：首选 Capacitor 6/7（维护活跃、插件生态好、cap sync 一键同步到 Gradle 工程）；若想零框架依赖，可用 Kotlin 原生 WebView 加载本地 index.html，体积最小、可控性最强。
  • 后端策略（关键）：Alphabounce 是单人打砖块玩法，核心游戏逻辑不需要服务端。把分数/存档从 Redis 改为 localStorage / IndexedDB；账号与"全球排行榜"作为可选模块，指向一个远程部署的 Node+Redis（Docker 上云），App 通过 HTTPS 调用。这样安卓包本身是纯前端、可离线。
  • 构建链：Haxe(js target, 沿用 frontend/build.hxml) → 打包为静态站点 → Capacitor sync → Gradle 构建 APK / AAB。

⑥ 从现有代码到安卓 APK 的迁移步骤

1
取 Eternal-Twin frontend/src（PixiJS 游戏主体），确认 build.hxml 能编译出 JS。
2
抽象 API 层：把对 backend 的调用抽成可配置接口（local / remote），默认走本地存储，避免安卓包依赖 Node。
3
Haxe 编译为 JS bundle，用 Vite 等打包成静态站点（index.html + 资源）。
4
加触摸控制：把鼠标/键盘输入映射为触摸事件（拖动控制挡板 Bouncer，点击发射）。这是原版没有、安卓必须的改造点。
5
npx cap init → cap add android → cap sync，生成 Android 工程。
6
Android Studio 打开 android/，Gradle 构建 release AAB / APK（上架用 AAB）。
7
真机测试：WebGL 性能、触控手感、不同分辨率适配、离线可玩性。

⑦ 风险与对策

  • WebGL 兼容性：个别低配机软件渲染慢 → 开启硬件加速 + PixiJS Canvas 回退 + 降低画质档位。
  • 输入方式：原版面向鼠标/键盘 → 必须做触摸映射（见步骤 4），否则无法操作挡板。
  • 包体体积：WebView 依赖系统内核，尽量用系统 WebView 而非内置内核；游戏资源本身很小。
  • Haxe 环境：需安装 Haxe 4.3.x + haxelib（前端已配置 haxelib.json），构建链要落地。
  • 后端依赖：若要做全球榜，需单独部署并解决跨域/鉴权；默认先不做，保证离线可玩。

⑧ 待确认的决策点

以下两点会影响最终落地形态，确认后我可以进一步给出可执行的工程脚手架：
  • 是否需要在线账号 / 全球排行榜？（决定要不要带 Node+Redis 后端；默认建议先纯前端离线版）
  • 分发方式：上架 Google Play（需 AAB + 合规）还是侧载/内部分发（APK 即可）？
  • 最低安卓版本目标？（默认 API 21 / Android 5.0，建议 24+ 覆盖面更好）
一句话总结：原版 Flash 路线已死，直接走 Eternal-Twin 的 Web 形态；用 WebView 封装（Capacitor 优先 / 原生 WebView 备选）+ PixiJS + 本地存储替代 Redis 即可在安卓上以最小成本跑起这个游戏，后端按需上云。
